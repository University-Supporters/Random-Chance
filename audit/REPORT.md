# GitHub 현행 코드 운영 적합성 검증

검사 대상: https://github.com/University-Supporters/Random-Chance/tree/4f514290e7b77773258e6075eda3549e3a9eb910

검사 기준 시각: 2026-09-18 22:39 KST부터. main의 검사 대상 소스·설정 31개 파일은 로컬과 일치했다. Git 명령은 사용하지 않았으며 GitHub 공개 읽기 API로 소스를 받았다. 실제 배포와 이 소스의 빌드 동일성은 서버의 빌드 식별자 제공이 없어 확정하지 않았다.

## 결론

300~500명 분량은 단일 로컬 Node 프로세스에서 처리 가능했다. 그러나 현재 운영 사이트의 저장 방식은 **Vercel Ephemeral Storage (/tmp)** 로 확인되어, 데이터 무손실을 보장할 수 없고 실사용 준비 완료로 판정할 수 없다. 영구 저장소와 인스턴스 간 원자적 동시성 제어가 우선 필요하다.

## 확인된 문제

### P0 — 현재 운영 저장소가 임시 디렉터리

`api/db.js:7`에서 Vercel은 기본 `/tmp`를 사용하고 메인·미러·스냅샷이 모두 같은 임시 디렉터리에 있다. 공개 health 응답에서도 해당 모드가 확인됐다. 별도 임시 디렉터리의 교체 인스턴스를 재현하면 기존 501명이 새 인스턴스에서는 0명으로 보인다. 기존 인스턴스의 파일이 유지되는 경우라도 목록이 인스턴스별로 갈릴 수 있다. 서버 백업은 별도 장애 영역이 아니다.

### P1 — 공유 KV에 두 인스턴스가 동시에 쓰면 성공한 등록이 유실

`api/db.js:13`의 queue는 해당 Node 프로세스 안에서만 동작한다. KV 어댑터는 JSON 전체를 읽은 뒤 조건 없는 SET을 수행한다. 두 독립 프로세스가 같은 버전을 읽도록 재현했을 때 두 등록 API가 모두 201을 반환했으나 공유 저장소에는 1명만 남았다. 이는 단순 실패 응답이 아니라 성공한 데이터의 유실이다. KV 연결만 추가해도 해결되지 않는다.

필요한 개선은 영구 DB의 학번·전화번호 UNIQUE 제약과 트랜잭션, 또는 Redis의 원자적 등록/버전 비교 후 저장이다. GitHub Contents 방식 역시 충돌 재시도·원격 제한을 별도로 검증해야 하며 이 검사에서 실 GitHub 쓰기는 하지 않았다.

### P1 — 두 실시간 사본 동시 손상 시 최근 스냅샷 이후 데이터가 빠짐

자동 스냅샷은 쓰기 시 5분 간격으로 생성한다(`api/db.js:92`). 2명 등록 성공 후 메인·미러를 동시에 손상시키면 이전 자동 스냅샷의 1명만 복구됐다. 최신 수동 스냅샷이 있을 때의 501명 복구 성공과는 다른 조건이다. 외부 지속 백업 또는 변경 로그가 필요하다.

### P1 — 기본 운영 비밀번호가 공개 소스에 존재

일반·상급 기본 비밀번호는 `server.js:10-11`에 공개되어 있다. 실제 운영 환경변수 값을 읽지 않았으므로 실제 서버가 기본값을 사용하는지는 확인하지 않았다. 기본값을 그대로 쓰는 경우 일반 운영자가 상급 기본 비밀번호를 알아내 정상 인증 경로로 진입할 수 있다. 이는 서명 위조나 미들웨어 우회가 아니라 비밀값의 공개 문제다. API 권한 분리 테스트 통과만으로 실제 접근 통제가 충분하다고 할 수 없다.

### P2 — 로그아웃은 이미 발급된 토큰을 서버에서 폐기하지 않음

`src/App.jsx`는 화면 메모리 토큰을 지우지만 서버 폐기 목록이나 logout API가 없다. 복사된 토큰은 원래 만료까지 일반 8시간·상급 30분 유효하다. 탈취된 토큰 위험에 대한 코드 검토 결과이며 실제 사용자 토큰은 수집하지 않았다.

### P2 — 로컬 금고 및 인증 시도 제한의 범위

Local Vault는 상급 인증 상태일 때만 동기화되며 약 10초 지연이 있다. 브라우저 저장 공간 삭제·다른 브라우저 사용·일반 관리자만 로그인한 운영 중에는 최신 복구본을 보장하지 않는다. 로그아웃 후 금고 데이터는 해당 브라우저 저장소에 남는다.

로그인 시도 제한 Map은 프로세스별 메모리라 인스턴스 교체·여러 인스턴스에 대한 전역 제한이 아니다. 제한의 존재만으로 서버리스 전체 무차별 대입 방어를 보장할 수 없다.

일반 참여자 목록 API는 당첨자 배열도 반환한다(`server.js:85`). 추첨 실행·초기화는 차단되지만, 당첨 결과 자체까지 상급 관리자만 보게 하려면 이 응답도 분리해야 한다.

## 판정 및 우선순위

1. 실제 사이트를 영구 저장소로 전환하고, 등록 원자성·중복 UNIQUE 제약을 함께 적용해야 한다.
2. 메인 저장소와 독립된 복구본 및 복구 가능 시점을 명시해야 한다. 현재 미러/스냅샷/금고를 무손실 4중 보호라고 표현하면 안 된다.
3. 기본 운영 비밀번호를 실제 배포에서 사용하고 있다면 교체해야 한다.
4. 이후 동일 500명/동시 요청/복구/권한 테스트를 실제 구성과 일치하는 스테이징에서 재실행해야 한다.

이번 작업은 요청한 현행 코드 검사다. 제품 소스의 동작이나 운영 데이터를 변경하지 않았다. 테스트·보고서 파일과 검증용 빌드 산출물만 생성했다. Git 명령을 실행하지 않았다.
